# This section contains data for testing sequential read operations

1.1 SMALL CONTENT BLOCK (1KB)
================================================================================
This is a small content block that simulates metadata or small artifact content.
The data in this block is designed to be read in a single operation to test basic
I/O performance differences between platform threads and virtual threads. While
the performance difference may not be significant for small reads, the cumulative
effect across many operations should demonstrate the benefits of Virtual Threads.

Java 21 Virtual Threads are designed to be lightweight and efficient for I/O-bound
operations. Unlike platform threads, virtual threads don't have a one-to-one mapping
with OS threads, allowing for much higher concurrency with minimal overhead.

This test data helps validate that the migration from Java 17 to Java 21 provides
the expected performance improvements for I/O operations in the Nexus Repository.
================================================================================

1.2 MEDIUM CONTENT BLOCK (10KB)
================================================================================
This medium content block simulates typical artifact content that might be stored
in a repository. The size is chosen to represent common library JAR files, small
packages, or documentation files that would be frequently accessed in a repository.

Virtual Threads in Java 21 are particularly beneficial for I/O-bound operations
like reading from files or network sockets. When a Virtual Thread performs a
blocking I/O operation, it doesn't block the underlying OS thread, allowing that
OS thread to be used by other Virtual Threads. This is in contrast to platform
threads, where a blocking I/O operation ties up the entire OS thread.

The following paragraphs contain repeated text to reach the desired block size.
This allows for testing read operations on content of various sizes to measure
the performance characteristics of Virtual Threads vs platform threads.

Virtual Threads are implemented using a technique called "continuation", which
allows the JVM to suspend and resume thread execution at well-defined points,
such as when performing blocking I/O operations. This enables efficient
multiplexing of many Virtual Threads onto a smaller number of OS threads.

One of the key benefits of Virtual Threads is that they eliminate the need for
complex thread pool management. With platform threads, developers need to
carefully tune thread pool sizes to balance resource usage with throughput.
Virtual Threads, on the other hand, can be created on-demand without worrying
about resource exhaustion, as they have minimal overhead.

In the context of Nexus Repository, Virtual Threads can significantly improve
the performance of operations like proxy repository fetches, file system
operations in the BlobStore, and database interactions. These operations are
typically I/O-bound and can benefit from the increased concurrency provided
by Virtual Threads.

The migration from Java 17 to Java 21 involves updating various components to
take advantage of Virtual Threads. This includes modifying executor services
to use Executors.newVirtualThreadPerTaskExecutor() instead of traditional
thread pools, and ensuring that I/O operations are performed in a way that
allows Virtual Threads to yield efficiently.

Testing with this data file helps validate that the migration has been
successful and that the expected performance improvements are realized.
By comparing the performance of the same operations using platform threads
and Virtual Threads, we can quantify the benefits of the migration.

Virtual Threads also simplify the code by eliminating the need for complex
asynchronous programming patterns. With platform threads, developers often
resort to callbacks, CompletableFuture, or reactive programming to achieve
high concurrency. Virtual Threads allow for simple, synchronous code that
is easier to write, read, and maintain, while still achieving high concurrency.

This test data file includes various patterns and sizes of content to simulate
real-world repository data. By testing with this file, we can ensure that
Virtual Threads perform well across a range of scenarios that Nexus Repository
might encounter in production environments.
